# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

"迷你四驅新手入門資訊站" (Mini 4WD Beginner's Guide Information Site) at https://mini4wd.parts/. It is a Traditional-Chinese-first Tamiya Mini 4WD site. Live today (**M1 closed 2026-09-20**): a car builder on the home page (kit or bare chassis, a slot list, compatibility-filtered part pickers, a rule engine that checks the build against a chosen race class, a 3D pane that draws all eight chassis and every fitted part from generated geometry, and the build kept in a shareable link), a parts database with per-part pages, category browsing and chassis pages, and the first guide. Planned: more guides, short links and votes (M2), and a beginner wizard (M4).

**Read `docs/PLAN.md` before implementing any feature.** It holds the agreed scope, phase order, data model, rule-engine design, hosting decisions and open questions. Supporting research with source URLs is in `docs/research/`. Do not re-research points already settled there.

## Current State of the Repo

- `main` is the only branch; the hand-managed `gh-pages` and the stale `master` are retired. `.github/workflows/deploy.yml` runs `npm test`, `npm run typecheck` and `npm run catalog:verify`, then builds, on push to `main` and GitHub Pages serves the Actions artifact (`build_type: workflow`).
- The site is a committed **Nuxt 4.5 + @nuxt/content v3 + @nuxt/ui v4** scaffold using the `app/` directory, with `@nuxtjs/i18n` on `prefix_except_default`. The builder **is** the landing page (`app/pages/index.vue`); `/build` is a redirect document left for old links. The catalog browses as a two-level hierarchy per locale, all of it enumerated in `nuxt.config.ts` from `content/` rather than crawled: `/parts` (a 29-card category grid), `/parts/category/<slug>` (the rows, with a chassis filter kept in the `#hash`), `/parts/<item number>`, plus `/chassis` and `/chassis/<id>`. **URLs are flat, end in a slash, and the hierarchy is declared** — `app/components/Breadcrumbs.vue` emits the trail and its `BreadcrumbList` JSON-LD, because GitHub Pages cannot 301 a URL that has already been shared (docs/PLAN.md §4.6). `@nuxtjs/sitemap` writes `/sitemap.xml` (850 URLs — 425 per locale — 316 KB, `/build` and image entries excluded) and `public/robots.txt` points at it. `/kits/…` pages do not exist: a kit row on a chassis page opens the builder on that kit instead, through `encodeBuild`. The nav reads 組車 (the builder at `/`), 指南, 零件, 底盤, 關於. `/guides` lists the guides; the first is `/guides/starter/` (2026-09-19), which recommends the three Starter Packs and ends in a button to the builder. A guide names kits through `:kit-links{ids="…"}` (`app/components/content/KitLinks.vue`, rows that open the builder on each kit) and sends the reader on with `::builder-cta` (`BuilderCta.vue`); both are content components, so a guide never restates a kit's name or picture by hand.
- **The UI is @nuxt/ui v4** (adopted 2026-09-22, `docs/PLAN.md` §4.1). Buttons, badges, the three picker dialogs, the base picker's tabs, the race-class radio group, the search inputs and the breadcrumb trail are all its components; `app/assets/css/main.css` is what no component covers — layout, the locale menu, the scene frame, the CJK rules and the perf hints. **Prefer a Nuxt UI component over hand-written markup**, with the exceptions below. Colour is named by role (`--ui-text`, `--ui-bg`, `--ui-border`) or by a step on `--color-chassis-*`, the site's own blue-grey written as a scale with `#2c3e50` at 500; **no colour literal belongs in main.css** outside that definition. `app/utils/emphasis.ts` decides whether a button reads as the page's action or one option among several, and `app/utils/severity.ts` what colour a finding wears — both so nine and two call sites cannot drift apart. Dark mode follows the system; two things are pinned to fixed steps because they are chrome rather than surfaces, the header and the plate under a product photo (every Tamiya photo is shot on white). Tailwind's Preflight is imported **whole**, with one `@layer base` block reverting the half this stylesheet was written over — heading scale, block margins, list markers, and the colour of a bare `a:not([class])`; every anchor Nuxt UI renders carries a class, which is what that selector is keeping clear of.
  - **`UApp` is deliberately absent, and the absence is load-bearing.** It is the provider root for toasts, `useOverlay` and tooltips; `UModal` is declarative and needs none, verified. Site-wide it cost 40.7 KB gz a route, on the builder alone 10.5 KB. The first thing that needs a toast brings it back, on its own route.
  - **`LocaleControls.vue` stays a hand-written `<details>`** — its links must be in the prerendered HTML so a crawler reaches `/en` (§4.6), and `UDropdownMenu` renders its panel client-side. It keeps its own CSS permanently.
  - `nuxt.config.ts` holds three settings that exist to stop the module shipping what the site never asks for, each with the measurement beside it: `ui.fonts: false` (the stack is the system one, so there is nothing to download), `ui.theme.colors` cut to the four aliases actually named, and `icon` listing six icons with `provider: 'none'` and `fallbackToApi: false` — a scan picked up Nuxt UI's *default* 45-name icon map and put it on all 1,713 pages.
- `content/` holds the generated catalog (382 parts, 8 chassis, 305 kits, and 176 body shells as JSON) plus per-locale prose under `content/zh-Hant/` and `content/en/` — `guides/` and `about/` only, since `/parts` became a real page. A new guide page is a Markdown file per locale plus its two routes in `nitro.prerender.routes`.
- The old baked hero model (`public/images/4wd.glb`) is gone with the model-viewer landing page, and so is its Tamiya photo `4wd.png`. The site-wide `og:image` is `public/images/og.jpg`, a 1200×630 capture of the builder pane (an Avante Mk.III Azure, shell lifted) on a `summary_large_image` card. A part page replaces it with its 320×240 detail thumbnail through `thumbnailShareMeta`, which downgrades the card to `summary` because 320 px is under what a large card wants; a chassis page instead names its own generated 1200×630 card through `cardShareMeta` and keeps the large one (both in `app/utils/shareImage.ts`).
- `public/thumbs/` holds 695 generated 160×120 product thumbnails (382 parts, 305 kits, 8 chassis, 2.7 MB) plus 320×240 copies under `parts-detail/` (382 files, 2.6 MB) and `chassis-detail/` (8 files, 53 KB), which only a detail page renders — the two collections with pages of their own. All are written by `npm run catalog:thumbs` and committed. `public/og/chassis/{zh-Hant,en}/` holds the 16 generated 1200×630 share cards (620 KB), written by `npm run catalog:og`: our own layout and wording around the detail thumbnail placed at its native size, per locale because the card is mostly words. Nothing enlarges a Tamiya photo. Rows with no photo draw an SVG slot icon from `app/utils/icons.ts` through `app/components/CatalogThumb.vue`. In the builder the base row shows the **chassis** thumbnail, and the kit's box art goes on the 車殼 (body) row only while that entry's `origin` is `kit` (`stockThumbFor` in `app/pages/index.vue`).

## Planned Architecture (see docs/PLAN.md §4)

- **Framework:** Nuxt 4, `nuxt generate` for static pages; server routes only for `/api/*` and `/b/:id` from M2.
- **Content:** @nuxt/content v3 collections with Zod schemas. Catalog data (parts, chassis, rules, guides, wizard profiles) is versioned YAML/Markdown in `content/`, keyed by Tamiya item number. Only user-generated data (builds, votes, view counts) goes to a database.
  - **Never import a *value* from `shared/catalog/schema.ts` into a page or component** — it drags Zod (60 KB) into that route's bundle. Types are free (erased); constants are not. `CHASSIS_IDS`, `isChassisId` and `byChassisOrder` live in the Zod-free `shared/catalog/chassis.ts` for this reason, and `share.ts` keeps its own tables for the same one. Check with `grep -l ZodError .output/public/_nuxt/*.js` and see which routes load that chunk.
  - **The budget this rule polices got tighter on 2026-09-22.** After @nuxt/ui, a catalog page carries ~191 KB gz of JS and the site ~31 KB gz of CSS, against ~132 KB and 4.5 KB before. Measure a change the way that one was measured — build, then sum the `_nuxt/*.js` a route's HTML actually references and gzip it — rather than reasoning about it. A component that lands on a route which needs nothing else from Nuxt UI drags reka-ui's core with it: that is why `UBreadcrumb` costs 23.5 KB gz on `/parts`, `/chassis` and the chassis pages and 2.6 KB everywhere else (kept anyway, owner 2026-09-22), and why its separator is a `›` rather than an icon.
- **UI:** @nuxt/ui v4 over Tailwind 4 and Reka UI, adopted 2026-09-22 against a measured cost (§4.1) rather than in spite of one. Prefer its components; see the exceptions in "Current State" above.
- **i18n:** @nuxtjs/i18n, `prefix_except_default`, `zh-Hant` default, `/en/`, later `/ja/`. Traditional Chinese is one page set: it reads in Hong Kong wording, because every Traditional Chinese name in the catalog comes from tamiya.hk. The HK/TW reader toggle was withdrawn on 2026-09-16 (`docs/PLAN.md` §4.1). `useWording` returns `hk` as a constant, but keep going through it (`:term{name="…"}` in prose — written `[:term{name="motor"}]{}` straight after a Chinese character, because MDC only starts an inline component after a space or one of `[*_(`, and a stray space shows in CJK text — `resolveName` in `shared/catalog/names.ts`) and keep storing the `tw` variants, so Taiwan wording can come back without touching the callers. Both `zh-HK` and `zh-TW` hreflang still point at the same URL. The header has one `<details>` locale menu, and its links must stay in the prerendered HTML so crawlers can reach `/en`. Part names for all locales live inline in each part record; guide bodies are separate Markdown files per locale, one @nuxt/content collection each.
  - **Write Chinese copy as 書面語 a reader in Hong Kong or Taiwan reads as natural** (owner, 2026-09-19, when every Chinese string was rewritten for that): no Cantonese-only words (淨底盤, 闊, 細 for "small", 螺絲批) and no Taiwan-only ones (螺絲起子, 卡榫); write around characters the two regions spell differently (裡/裏, 著/着, 甚麼/什麼, 這裡). The site's terms: 輪圈 (not 輪框), 薄胎 for low-profile, 光面 for slick, 導電片 for terminal, 原裝… for a kit's stock piece, 純底盤 for a bare chassis, 小徑/大徑, and car and motor names in English as tamiya.hk prints them. 摩打/剎車 still go through `:term`.
- **3D:** plain three.js (no TresJS, decided 2026-09-16, see `docs/PLAN.md` §4.1 and §5.5) in one `.client.vue` scene component, mounted on the home page (the builder) after hydration, client-only and code-split, behind a poster image that holds its space; it draws the empty MA proxy car before anything is chosen, and all eight chassis once one is chosen. The same component serves the home page and will serve part previews; Google `<model-viewer>` has been removed. Part and body shapes are three.js geometry generated in the browser, parts from their catalog specs and a body from a per-kit silhouette table authored from box art so it roughly resembles that kit's car, never GLB files and never Blender models (docs/PLAN.md §5.6). The chassis follow the same rule: all eight are generators in `shared/scene/generators/chassis.ts` over the same box/prism/revolve helper, with their sockets in `shared/scene/sockets.ts`, and no GLB or loader ships (decided 2026-09-16, §5.6).
- **Hosting:** M1 stays on GitHub Pages. M2 moves to Cloudflare Workers with static assets, D1 (builds, votes), R2 (thumbnails), Turnstile (abuse control), nuxt-og-image for share cards.
- **Rule engine and wizard:** declarative JSON rules (slot capacity, chassis compat, motor shaft type, class legality, dependencies, numeric limits) evaluated client-side and re-validated server-side; the wizard is a weighted scorer over the same catalog, no ML.

## Domain Notes

- Race classes: Tamiya **Open** (official regulation), Tamiya **Stock Class** (ストッククラス / 基礎賽, since 2025), and **B-MAX GP** (unified with Stock Class in Dec 2025). "**B-Stock**" is local shorthand for Stock Class (owner-confirmed 2026-09-08); model it as an alias of Stock Class, not a separate ruleset. "Box Stock" is a different, stricter shop class.
- Chassis in v1 scope: MA, MS, ME, AR, FM-A, VZ, Super-II (+ VS). PRO chassis (MS/MA/ME) need double-shaft motors; all others single-shaft.
- Item numbers: 18xxx / 19xxx kits, 15xxx regular Grade-Up Parts, 95xxx limited/special, 94xxx older limited.
- Regulation envelope: 105 × 165 × 70 mm, ≥ 90 g with batteries, tires 22–35 mm, 2×AA.

## Data and IP Rules

- Primary data source is the Tamiya Japan product catalog plus its per-chassis compatibility pages (`product_info_ex.html?genre_item=mini4wd_chassis_*`); secondary sources are tamiya.hk's public store API (HKD prices, TC category names) and Fandom / Wikipedia (CC-BY-SA, attribute).
- Store **facts** (item number, names, price, release date, dimensions, compatibility) and our own text. Do not copy Tamiya descriptions or redistribute Tamiya PDFs. Prefer own photos for parts shown in the builder.
- **Product pictures: self-hosted thumbnails, never hotlinks** (owner, 2026-09-16, reversing the 2026-09-09 hotlink decision). `npm run catalog:thumbs` downscales Tamiya's photo to 160×120 WebP in `public/thumbs/{parts,kits,chassis}/<id>.webp`; nothing on the site may reference `cloudfront.net` or any Tamiya image URL at render time. Hotlinking is legally safer (the US server test) but spends Tamiya's bandwidth on every page view and puts us in their logs daily, which is the risk that actually bites. What keeps the copies defensible is that they are small, credited on the page (`build.imageCredit`), beside a link to Tamiya's own product page, and confined to one directory so a takedown is `rm -r`. The full-size `officialImage` URL stays in the catalog as a fact and is never rendered.
- **Our licences** (owner, 2026-09-17): source code is GPL-3.0-or-later (`LICENSE`), our own assets are CC BY-SA 4.0 (`LICENSE-ASSETS`). The README's 授權 Licence section lists which paths each covers and what neither covers: `public/thumbs/` (© TAMIYA), `public/og/` (our layout around a © TAMIYA thumbnail), the Fandom-derived fields (the wiki's own, unversioned CC BY-SA) and `data/raw/`. The 3D generators are code; only rendered images such as the posters are assets. A new top-level directory needs a line in that section.
- 3D assets must be simplified, stylised representations generated procedurally or modelled in-house. Never offer GLB downloads. Keep the "unofficial fan site" disclaimer.
- Traditional Chinese terminology differs between Hong Kong (摩打, 剎車) and Taiwan (馬達, 煞車); store both variants where they differ.

## Catalog Pipeline

- `content/parts/*.yml`, `content/chassis/*.yml`, `content/kits/*.yml` and `content/bodies/*.json` are **generated** — never hand-edit them. Corrections go in `data/overrides/parts.yml`, `data/overrides/kits.yml` (both keyed by Tamiya item number), `data/chassis/*.yml` or `data/bodies/*.yml`, then `npm run catalog:generate`.
- A **body shell** is the shape the 3D pane draws over the chassis: a few dozen numbers per car in `data/bodies/<id>.yml`, authored from the box art against `data/bodies/README.md`, which is the format and the loop. 176 shells cover all 305 kits. A kit is matched by the wiki article its loadout came from, or listed by item number where no article reaches it. `npm run catalog:bodies` renders a shell beside its box art into `.cache/bodies/` (`--todo` lists the cars still on the default wedge, `--art=<kit>` fetches a photo to read).
- `npm run scrape` refreshes `data/raw/*.json` (throttled, disk-cached under `.cache/`; `--only=jp,kits,compat,chassis,hk,fandom` limits it to one source); `npm run catalog:thumbs` fetches and downscales the product photos into `public/thumbs/` (two sizes for parts and chassis — the 160×120 row thumbnail and the 320×240 `<collection>-detail` copy a detail page leads with; `--only=parts-detail,chassis-detail` runs just the second pass) — it reads which items exist from `content/`, so a brand-new item needs `catalog:generate` → `catalog:thumbs` → `catalog:generate`, the second pass being what writes the `thumbnail` path onto the record; `npm run catalog:og` draws the chassis share cards from the photos `catalog:thumbs` already fetched, so it needs no network and runs after it; `npm run catalog:report` lists what still needs a human; `npm run catalog:crossref` audits our derived categories against the Fandom wiki's hand-written ones and prints disagreements to review; `npm run catalog:verify` validates the committed YAML; `npm test` runs the parser fixtures; `npm run typecheck` runs both halves: `typecheck:scripts` (`scripts/` and `shared/` on TypeScript 7 — nothing else checks them, Node strips the types at runtime) and `typecheck:app` (`app/` and `nuxt.config.ts`, via the root `tsconfig.json`, through `vue-tsc`, which cannot run on TypeScript 7, so `scripts/typecheck-app.ts` points it at the `typescript6` alias).
- The Fandom wiki plays two roles, and they have different rules. `data/raw/fandom-parts.json` is **a QA source plus one field**: it exists because our categories come from ordered substring rules over Japanese names, whose one failure mode is a short keyword swallowing a longer word (シール ate シールド), and the only thing `content/parts` takes from it is `fandomTitle` — the article covering a part's product family (121 of 382 parts, owner 2026-09-16). That one field is what a part page links to and what groups an item number with its other colours; no wiki *text* is imported. `data/raw/fandom-kits.json` **is** imported into `content/kits`, because Tamiya publishes no bill of materials for a kit and the wiki's `Technical Info List` is the only structured source for what is in the box. Both are CC-BY-SA: each kit carries `loadoutSourceTitle` so kit pages can attribute on the page itself, not only on the attribution page.
- A kit's chassis comes from Tamiya's chassis tag (present on every kit detail page), never from the kit's name. Its gear ratio and stock wheels/tires come from the wiki — Tamiya prints a gear ratio on about 5% of kit pages.
- What a kit or a bare chassis puts in each slot is a `loadout`: slot id → entries that carry a `partId`, a free-text `label`, or both. Most of what comes in a box is moulded plastic that Tamiya never sold as a Grade-Up Part, so a label with no item number is the normal case, not a gap. A chassis' `defaultLoadout` is the base; a kit's `stockLoadout` is only the delta over it. When a stock piece is sold as a real product, the loadout names it by `partId` (the AO-1001 motor and the AO-1004/AO-1044 propeller shafts on the five single-shaft chassis). That part must also be chassis-compatible, or the picker hides it once swapped out: `catalog:verify` checks a loadout part against the slot type, not the chassis, so fix the gap with a `chassisCompat` override, which `generate` marks `source: override`.
- A **parts set** (`category: bundle`, the five ファーストトライパーツセット) carries `contents`: slot id → item numbers, authored in `data/overrides/parts.yml` and nowhere else, from which `catalog:generate` derives the set's own `slots`. The builder fits a set whole — from its part page or from any picker it appears in — because a build holds item numbers only (docs/PLAN.md §4.9). A piece Tamiya sells separately is named by its item number where Tamiya's own contents sentence names that product; every other piece is the set's own item number standing in the row, because the set is the only way to buy it.
- Scripts are plain `.ts` run by Node's native type stripping — no build step, and relative imports need explicit `.ts` extensions.
- Tamiya's pages are Shift_JIS: decode with `new TextDecoder('shift_jis')`. Strict Shift_JIS decoders truncate the pages.

## Development Notes

- Commit messages follow the existing gitmoji style (see `git log`).
- Analytics: GA4 (`G-GJ34BG7E3W`) and PostHog (`phc_tAY3onBYUoZPu78wMTfTYpTLGNivkjrKLJyDd9aDcsnR`, Cloud US) both load through `@nuxt/scripts`, configured in `scripts.registry` in `nuxt.config.ts` — `proxy: false` on both, `bundle: false` on GA, `autocapture: false` on PostHog, for the reasons written there. **Send every event through `useAnalytics().track()`** (`app/composables/useAnalytics.ts`): it fans out to both SDKs with the same name and properties, and its `AnalyticsEvents` map is the list of what exists. Ids, never localised names — a name splits each report in two. A new property is a new GA4 custom dimension to register by hand. PostHog counts pageviews itself; GA gets them from `app/composables/useAnalyticsPageViews.ts`, which also keeps gtag's current page up to date so events are not all filed under the landing page.
- The site is bilingual today (Traditional Chinese primary, English secondary) and targets Mini 4WD beginners and hobbyists.
